# Issue #80：需求评估与设计取舍

## 评审结论

基线 `a37c7957391b9408ad295b948a2a05fb6fd99a09` 上，四报告规范与模板已存在，但没有状态机、严格机器块、公开摘要验证器、轮次预算或对应测试。因此 #80 的核心断言成立，不能因历史本地原型或人工流程文档存在就关闭 Issue。实现范围以[需求文档](audit-metadata-requirements.md)中的 80.1～80.6 为准。

## 冲突与解法

现有 `docs/development/CICD_WORKFLOW.md` 约束独立评审后的产品修复必须获准，原 `REVIEW_GUIDE.md` 也有人工决定节点；Issue #80 则要求审计 finding 不再逐条等待人工批准。两者不能通过删除权限边界来“对齐”。本次采用双层区分：

1. 审计元数据层允许 Reviewer 和 Codex 在既定主题内登记、核验、复核、延期和有限重试，不设 finding 级人工状态节点。脚本只管理文件与统计，本身无产品写操作。
2. 产品交付层仍由当轮用户请求决定是否可以修代码及远端交付；有需求扩展、预算或不安全取舍时先延期并提交人工判断。运行时高风险审批仍独立存在。

因此不改 canonical CI/CD 入口、Actions 或 required context；在评审指南中说明两层边界，而不把审计流程伪装成产品交付授权。

## 数据与状态选择

- 机器块使用严格 JSON，正文留给可核查证据。状态推进只读机器块，不尝试理解自由文字。
- 基线锁定完整 SHA、分支和主题；Reviewer 的子编号必须归属已选主题。原 REVIEW 登记后按哈希冻结，角色只能写自己的报告。
- 一次 `advance` 只做一步，状态持久化在私有文件。进入修复前占用轮次，避免重启、失败或重复调用“赠送”额外尝试。
- 第二轮保持所有 finding 的复核覆盖，但只有 `retryIds` 可改变处置和复核结论；非重试项沿用首轮已登记结论，首轮报告原样快照并校验哈希。
- 摘要通过固定字段白名单生成，validator 独立拒绝额外字段和数量矛盾。指标只基于本轮最新已登记快照；未有分母时返回 N/A。

## 风险与限制

| 风险 | 处理方式 | 仍然存在的边界 |
| --- | --- | --- |
| Agent 在正文和机器块写出相互矛盾的判断 | 文档要求逐项对齐，脚本校验机器字段与状态关系 | 无法自动理解任意中文证据，仍需人工/独立复核内容真实性 |
| 私有报告被意外覆盖 | 不覆盖历史目录；登记后保存哈希与首轮快照 | 本地操作者可直接篡改所有文件；哈希不是恶意对抗安全隔离 |
| 审计摘要泄露信息 | 严格字段白名单、标签字符约束、敏感模式拒绝、提交前审查 | 不能识别所有伪装的秘密或私人语义 |
| 两轮预算被误解为强制重试 | 仅明确可安全修复的残余 defect 才可进入第二轮 | 证据不足、环境问题和需求取舍会以 incomplete 或延期结束 |
| 审计工具被误当成发布门禁 | CI、Release Please 和 ruleset 不引用审计状态 | 审计结论不证明产品生产可用 |

## 评审与发布口径

本文件是对 Issue 需求的工程评估，不是 Claude Code 对产品缺陷的独立鉴定，也不替代 `CURRENT_BASELINE/REVIEW/FIX_REPORT/VERIFICATION` 的具体轮次报告。实际检查、结果和未执行项以[证据文档](audit-metadata-evidence.md)及私有原始输出为准。功能交付须经 PR 的 required CI；是否合并、是否合并随后生成的版本 PR，分别按用户授权和 canonical 工作流判断。
